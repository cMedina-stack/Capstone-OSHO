# OSHO — Occupational Safety & Health Oversight

React/Vite frontend, Express API, and PostgreSQL database for campus hazard and incident reporting.

## Run locally

1. Install dependencies with `npm ci --prefix backend` and `npm ci --prefix frontend`.
2. Create `backend/.env` using `backend/.env.example`. Keep credentials out of source control.
3. For an **empty PostgreSQL database only**, import `backend/database-schema.sql` with `psql`. This is a schema-only snapshot; it contains no users or reports. Never import it over an existing database.
4. Run `npm run migrate --prefix backend` to apply outstanding migrations. The runner is transactional and records each migration once. Existing records are preserved; duplicate assessments cause migration failure rather than deletion.
5. Run `npm run dev --prefix backend` and `npm run dev --prefix frontend` in separate terminals. Vite proxies `/api` to port 5000.

Existing installations only need step 4 for the database changes in this update. Use an existing administrator account; account creation at `POST /api/users/batch-register` now requires an administrator token. For a fresh database, use the explicit bootstrap script documented below.

## Workflow

- Employees record a hazard or incident, view their reports, and submit an assessment.
- An assessment save sets report and assessment to `under_review`, with review status `pending`. Editing approved content also restarts review.
- Administrators can request a revision with remarks or approve an assessment. Approval sets the assessment to `action_required`; the report stays `under_review`.
- Once work is accomplished, an administrator enters the accomplished date and selects **Confirm completion & resolve**. Completion requires prior approval, and sets both report and assessment to `resolved`.
- The map includes risk from both report types. Resolved and rejected reports do not contribute to active building risk. Historical report counts remain available.
- Employees can access only their own full reports and assessments. Authenticated campus map views contain safety summaries; administrative views require the admin role.

Hazard risk is generated by PostgreSQL from likelihood × severity. Incident assessments store initial and optional residual risk. Scores use Low (1–4), Moderate (5–9), High (10–16), and Critical (17–25). Calendar date inputs remain date strings; backend completion-date checks default to `Asia/Manila`.

## Verification

```sh
npm run lint --prefix frontend
npm run build --prefix frontend
npm test --prefix backend
npm run test:integration --prefix backend
```

The integration test uses the configured database and a local HTTP server. It creates fixtures inside one outer transaction and rolls them back, exercising login, account permissions, report ownership, both assessment workflows, maps, and dashboards. Identity sequences may advance even though records roll back. Do not run concurrent requests through that test server; its transaction adapter is for serial verification only.

The production frontend uses relative `/api` URLs. Configure your web server to forward `/api` to Express and serve `frontend/dist/index.html` for frontend routes. Vite's development proxy does not configure production hosting.

## Initial administrator

On a fresh database with no administrator, set `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` (at least 12 characters), `BOOTSTRAP_ADMIN_FIRST_NAME`, and `BOOTSTRAP_ADMIN_LAST_NAME` in your shell, then run `npm run bootstrap-admin --prefix backend`. The script refuses to run if an administrator already exists and does not print the password or hash. Afterwards, unset the bootstrap variables.

## Optional browser verification

Install Playwright outside the project or in your development environment, download its Chromium browser, and build the frontend. Run `scripts/verify-workflows.js` from `backend` with `OSHO_BROWSER_TEST=1`. If Playwright is outside the project, set `PLAYWRIGHT_MODULE` to its package directory and `PLAYWRIGHT_BROWSERS_PATH` to its browser cache. This uses the same rollback-only fixtures and exercises the built frontend through Chromium. The browser helper is not loaded during normal API tests or server startup.

## Assessment Excel exports

Administrators can open **Reports & Assessments**, choose the type/status/search filters, and select **Download Excel**. The server generates a fresh `.xlsx` from saved database assessments each time; unsaved edits and reports without an assessment are excluded.

With all report types selected, the workbook contains **Hazard Assessments** and **Incident Assessments** sheets. Selecting a single report type exports only that sheet. Each register includes report and assessment identifiers, location, assessor, risk ratings, actions, responsible unit, deadlines, completion dates, and review status. Incident exports additionally include findings, cause analysis, consequences, and residual risk. Pending or revision-required records are clearly labeled; exporting does not approve them.

The authenticated admin endpoint is `GET /api/admin-assessments/export?type=all&status=all&search=`. It returns a dated download, disables response caching, and rejects exports larger than 10,000 assessments instead of truncating them. The workbook uses [ExcelJS](https://github.com/exceljs/exceljs) and requires no database migration. No file is stored on the server.
